# Git 与发布规则

## 工作区完整性

- 编辑前后分别检查 `git status --short` 和相关 `git diff`。
- 不提交运行日志、临时测试目录、缓存、构建产物、用户备份、真实数据或本机绝对路径。
- 生产代码导入的新增文件必须被纳入提交；不得留下只在当前脏工作区可运行的提交。
- 提交前运行 `git diff --check`，并确认删除、重命名和未跟踪文件都符合意图。
- 工作区过大时按行为和依赖关系拆分提交，但不能把一个不可运行的中间状态伪装成独立提交。

## 提交范围

- `D:\chatgpt2api` 与 `D:\nanocat` 是两个独立仓库，必须分别查看差异、测试和提交。
- 用户只说“提交”时，不自动包含另一个仓库；汇报中明确每个仓库是否有未提交或未推送内容。
- 不修改、不压缩、不重写用户已有提交，除非用户明确要求。
- 未经明确授权，不执行 push、tag、GitHub Release、镜像构建/推送或 npm 发布。

## Nanocat 到宿主的发布顺序

1. 宿主开发阶段临时接入 `D:\nanocat`，完成真实页面联调。
2. 在 Nanocat 运行 check、build 和相关 E2E，并独立提交。
3. 由用户验收宿主中的实际效果。
4. 用户明确授权后更新 Nanocat 版本、Changelog，并执行 npm 发布。
5. 确认注册表中的新版本后，宿主切换到正式 npm semver，重新安装依赖。
6. 在宿主运行 runtime 测试和生产构建，再独立提交依赖切换。

不得跳过用户验收直接发布，也不得把 `file:D:\nanocat`、`file:../../nanocat` 或临时 tarball 当作最终发布依赖。

## 版本与文档

- 用户可感知的功能、Interface 或行为变化更新 `CHANGELOG.md` 的 Unreleased；纯内部重构无需逐条记录。
- 当前文档只描述已验证行为。删除路由或功能时，同一修改删除对应的 current 文档内容。
- 计划文件不是发布记录；过期计划应删除或明确标为 historical，不能继续挂在 current 文档索引中。
- 版本号、tag、npm 包和容器标签必须指向同一已验证提交；未明确发布时不提升版本。
